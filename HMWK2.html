From Wallet Seed to Ethereum Address

A clear guide to hashing, key derivation, and cryptographic tools in Ethereum wallets.

1. The Ethereum Wallet Pipeline

An Ethereum wallet does not store just one secret number. It starts with random data and uses specific mathematical steps to create addresses. Here is the full pipeline:

Mnemonic Phrase (typically 12, 18, or 24 words) ↓ [BIP-39] PBKDF2 function (+ optional passphrase) Seed (512-bit binary number) ↓ [BIP-32 / BIP-44] Derivation path: m/44'/60'/0'/0/0 Private Key (256-bit scalar) ↓ [secp256k1] Elliptic curve point multiplication Public Key (64 bytes, uncompressed coordinates X and Y) ↓ [Keccak-256] Sponge hash function (drop first 12 bytes) Ethereum Address (20 bytes / 40 hexadecimal characters) ↓ [EIP-55] Checksum capitalization rule Checksummed Address (e.g. 0x9858EfFD232b4033E47D90003D41EC34EcaEDa94)

Any change to a valid mnemonic phrase or its optional BIP-39 passphrase produces a different seed, which in turn derives a different wallet key hierarchy and, with overwhelming probability, a different Ethereum address.

2. Roles of Standards and Cryptographic Primitives

Primary Source Reference: Arigbanla, O. (2024). BIP 32, 39, and 44: Hierarchical Deterministic Wallets and Mnemonic Phrases. Medium.

BIP-39 — Mnemonic Phrase and Seed Generation

As explained by Arigbanla (2024), BIP-39 provides a human-friendly way to back up and restore a master seed. Instead of copying long binary numbers, BIP-39 turns random entropy into a standard sequence typically of 12, 18, or 24 words from a fixed word list of 2048 words. Then, it uses PBKDF2 with 2048 rounds of HMAC-SHA512 to turn the phrase and an optional passphrase into a 512-bit binary seed. This standard ensures that different wallet applications (like MetaMask, Rabby, or Exodus) can read the same phrase and calculate the exact same seed.

BIP-32 — Hierarchical Deterministic (HD) Key Derivation

BIP-32 is the key derivation standard that creates an entire tree of keys from one master seed (Arigbanla, 2024). Because the derivation is deterministic, the same parent key always gives the same child keys. A user only needs a single backup of the master seed to recover all present and future addresses. BIP-32 defines two types of child keys:

  • Non-hardened keys: Allow a wallet to create child public keys without touching private keys. However, if a non-hardened child private key and the parent public key are both leaked, an attacker can calculate the parent private key.
  • Hardened keys: Prevent this risk. Knowing a hardened child key does not let anyone compute the parent key or sibling keys.

BIP-44 — Standard Multi-Account Hierarchy

BIP-44 is a specific structure built on top of BIP-32 (Arigbanla, 2024). It organizes keys into a clean tree using purpose, coin type, and account levels: m / 44' / coin_type' / account' / change / address_index. For Ethereum, the coin type is registered as 60' (Bitcoin is 0'). This allows a single wallet to organize multiple accounts and different cryptocurrencies in separate subtrees while maintaining complete deterministic recovery.

secp256k1 — Elliptic Curve Cryptography

secp256k1 is the elliptic curve used by Ethereum's traditional externally owned accounts (EOAs). It is used to derive public keys from private keys through elliptic curve scalar multiplication. Computing a public key from a private key is computationally efficient, whereas recovering the private key from the corresponding public key is considered computationally infeasible with currently known classical algorithms and appropriately chosen parameters. This security assumption is based on the Elliptic Curve Discrete Logarithm Problem (ECDLP).

Keccak-256 — Hash Function

Keccak-256 hashes the 64-byte public key representation consisting of the concatenated X and Y coordinates, excluding the 0x04 prefix used in the uncompressed public key encoding. The resulting digest is 32 bytes long. Ethereum derives the 20-byte (160-bit) account address by dropping the first 12 bytes and retaining the last 20 bytes of this digest.

EIP-55 — Mixed-Case Checksum

Raw Ethereum addresses are commonly represented using lowercase hexadecimal characters, which do not provide an explicit checksum. EIP-55 introduces a mixed-case checksum by determining the capitalization of hexadecimal letters according to the Keccak-256 hash of the ASCII-encoded lowercase hexadecimal address. This mechanism can detect many typing errors, although it does not guarantee detection of every possible error. Wallets may use the checksum to warn users when an address has an invalid checksum before a transaction is sent.

3. Core Cryptographic Concepts: Clear Distinctions

It is important not to confuse these core cryptographic mechanisms:

Concept Rigorous Definition Reversibility & Behavior Role in Wallet
Key Generation Sampling true random entropy using a CSPRNG. It converts entropy (with a checksum) into mnemonic words; it does not pick 12 independent random words directly. Non-deterministic process Sampling initial 128-bit entropy and generating mnemonic words (BIP-39).
Key Derivation Computing child keys deterministically from a parent secret using pseudorandom functions. Deterministic; some parent keys can be recovered in non-hardened BIP-32 leaks Expanding master seed into child keys (BIP-32 / BIP-44).
Public-Key Cryptography Asymmetric key pairs based on elliptic curve math (secp256k1). Private keys are never broadcast over the network. Trapdoor (infeasible to invert without private key) Authorizing transactions through ECDSA digital signatures.
Hashing Mapping arbitrary data to a fixed-size digest. Designed to be computationally infeasible to invert, though not a mathematical guarantee against all preimages. One-way design (preimage resistant) Compressing the 64-byte public key into an address (Keccak-256).
Checksum Error-detecting code embedded directly into the representation (such as mixed-case hex capitalization). Verification only Detecting many typing mistakes in Ethereum addresses (EIP-55).
Encoding Bijective conversion of binary data representation into a specific format without losing information. Fully reversible Representing raw bytes in Hexadecimal or Base58 format.

Note: An ECDSA signature authorizes a transaction via cryptographic signature verification; the secret private key itself is never transmitted across the network.

4. Statistical and Mathematical Properties

1. Entropy Propagation

A standard 12-word mnemonic starts from 128 bits of true random entropy, appends a 4-bit SHA-256 checksum, and splits the resulting 132 bits into twelve 11-bit chunks. Stretching this data with PBKDF2 produces a 512-bit seed, but this conversion does not increase secret entropy: the output space is bounded by the original 128 bits. The 2048 PBKDF2 iterations increase computational work for offline attacks, but long-term security fundamentally depends on the initial entropy and the optional passphrase strength.

2. The Avalanche Effect

Cryptographic hash functions like Keccak-256 exhibit a strong avalanche effect: changing a single bit in the input typically changes approximately 50% of the output bits. While this statistical spreading prevents predictable patterns, collision resistance and preimage resistance require separate, rigorous cryptographic properties beyond avalanche metrics alone.

3. Collision Space vs. Targeted Preimage

An Ethereum address is 20 bytes (160 bits), giving an address space of 2160 ≈ 1.46 × 1048. It is essential to distinguish between two problems:

  • Targeting a Specific Address (Preimage Resistance): Finding a private key whose derived address matches a specific, targeted victim address requires approximately 2160 operations for an ideal hash model.
  • Collision Resistance (Any Two Addresses Colliding): Finding any two distinct keys that produce the same address requires approximately 280 operations, governed by the Birthday Paradox.

These values represent theoretical bounds for an ideal hash model rather than unconditional security guarantees for every real-world implementation.

4. EIP-55 Error-Detection Power

EIP-55 provides an average of approximately 15 check bits per address. According to the official EIP-55 specification, the probability that a randomly generated address containing a typing error accidentally passes the checksum is approximately 0.0247%, corresponding to an error-detection rate of about 99.9753% under standard model assumptions. This value reflects the empirical error detection under the specification model rather than an absolute guarantee against every possible human error.

5. Historical Timeline and Evolution

These cryptographic algorithms and wallet standards emerged over several decades:

  1. 1977 — RSA: Landmark publication of public-key cryptography by Rivest, Shamir, and Adleman (following early theoretical foundations like Diffie-Hellman).
  2. 2001–2002 — SHA-2 / SHA-512: Published by NIST in 2001 and formalized in FIPS 180-2 (2002); used inside BIP-39 and BIP-32 HMAC functions.
  3. 2012 — BIP-32 (February 11, 2012): Pieter Wuille proposed Hierarchical Deterministic wallet trees to replace one-time backup models.
  4. 2012 — Keccak Wins NIST Competition (October 2012): Keccak was selected as the winner of the SHA-3 cryptographic competition.
  5. 2013 — BIP-39 (September 10, 2013): Introduced human-readable mnemonic wordlists and PBKDF2 seed stretching.
  6. 2014 — BIP-44 (April 24, 2014): Standardized multi-account, multi-coin derivation paths across blockchains.
  7. 2015 — SHA-3 / FIPS 202 (August 2015): NIST published the final standard, incorporating domain separation padding.
  8. 2016 — EIP-55 (January 14, 2016): Vitalik Buterin created the mixed-case address checksum proposal to prevent loss of funds from typing errors.

Key Distinction: Keccak-256 vs NIST SHA3-256

Ethereum uses Keccak-256, not NIST SHA3-256. NIST modified the padding rule (inserting byte 0x06) when finalizing FIPS 202 in 2015. Ethereum had already launched using original Keccak padding (0x01). Updating the hashing function would have broken compatibility with deployed contracts and accounts.

6. Why Not Use Just One Algorithm for Everything?

A single algorithm cannot efficiently or appropriately fulfil every cryptographic and organisational requirement of a wallet. Instead, the Ethereum wallet pipeline combines complementary standards and cryptographic primitives, each designed for a specific purpose:

  • BIP-39: Converts random entropy into a human-readable mnemonic phrase and derives a seed for wallet recovery.
  • BIP-32 / BIP-44: Enable hierarchical key derivation and define a conventional structure for organising accounts and addresses.
  • secp256k1: Provides the elliptic curve mathematical foundation for deriving public keys from private keys and supports ECDSA digital signatures.
  • Keccak-256: Provides cryptographic hashing used to derive traditional Ethereum externally owned account (EOA) addresses from public keys.
  • EIP-55: Defines a mixed-case checksum representation that helps detect typing errors in displayed Ethereum addresses.

These components address distinct requirements: recoverability, key organisation, authentication, address derivation, and error detection. Combining them creates a practical and interoperable wallet architecture while keeping each responsibility conceptually separate. No single component replaces the others, because each solves a different problem.
